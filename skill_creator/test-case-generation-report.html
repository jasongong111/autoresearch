How to Generate Test Cases for a Skill

This guide covers the complete workflow for creating, running, and evaluating test cases (evals) for AI assistant skills using the skill-creator toolkit. Test cases verify that a skill produces correct, high-quality outputs when invoked by an agent.

1. Overview

A skill is a reusable instruction set (in SKILL.md) that tells an AI agent how to perform a specialized task. Test cases ensure the skill works as intended across different inputs.

The skill-creator evaluation system compares two configurations for each test case:

  • With skill — The agent has access to the skill's instructions and bundled resources.
  • Without skill (baseline) — The agent receives only the raw user prompt, with no skill guidance.

By comparing these configurations, you can objectively measure whether the skill adds value.

When Test Cases Are Needed
Skills with objectively verifiable outputs (file transforms, data extraction, code generation, fixed workflow steps) benefit greatly from test cases. Skills with subjective outputs (writing style, art) are better evaluated qualitatively by a human.

2. The Evals Schema

Test cases are stored in evals/evals.json inside the skill directory. 

{
  "skill_name": "example-skill",
  "evals": [
    {
      "id": 1,
      "prompt": "User's example prompt",
      "expected_output": "Description of expected result",
      "files": ["evals/files/sample1.pdf"],
      "expectations": [
        "The output includes X",
        "The skill used script Y"
      ]
    }
  ]
}

Field Reference

skill_name
string
Name matching the skill's frontmatter name field.
evals[].id
integer
Unique identifier for the eval.
evals[].prompt
string
The task to execute. Should be realistic and specific.
evals[].expected_output
string
Human-readable description of what success looks like.
evals[].files
string[]
Optional list of input file paths, relative to the skill root.
evals[].expectations
string[]
Verifiable statements used by the grader agent. Add these after drafting the skill.

3. Step-by-Step Workflow

Phase 1: Draft the Skill

  1. Define what the skill should enable the agent to do.
  2. Decide when the skill should trigger (user phrases/contexts).
  3. Determine the expected output format.
  4. Write the SKILL.md with YAML frontmatter and markdown instructions.

Phase 2: Create Initial Test Prompts

After writing the skill draft, create 2-3 realistic test prompts — the kind of thing a real user would actually say. Share them with the user for approval.

Save prompts to evals/evals.json. Do not write assertions yet — just the prompts and expected output descriptions.

Phase 3: Run Test Cases

For each test case, spawn two subagents simultaneously:

  • One with the skill (reads the skill's SKILL.md)
  • One without the skill (raw prompt only, as a baseline)

Launch all runs in the same turn so they finish around the same time. Store results in a workspace directory like <skill-name>-workspace/iteration-1/eval-<id>/.

Phase 4: Draft Assertions (While Runs Execute)

Don't wait idle. While runs are in progress, draft quantitative assertions for each test case. Good assertions are objectively verifiable and have descriptive names that read clearly in the benchmark viewer.

Avoid Subjective Assertions
Don't force assertions onto things that need human judgment (e.g., "the design looks good"). Use qualitative review for subjective outputs and assertions for objective, checkable criteria.

Phase 5: Grade, Aggregate, and Review

  1. Grade each run — Evaluate assertions against outputs and transcripts. Save to grading.json.
  2. Aggregate — Run scripts.aggregate_benchmark to produce benchmark.json with pass rates, timing, and token stats.
  3. Analyze — Surface patterns hidden by aggregate stats (non-discriminating assertions, flaky evals, tradeoffs).
  4. Review — Launch the eval viewer so the human can inspect outputs and leave feedback.

Phase 6: Iterate

Read the feedback, improve the skill, and rerun all test cases into a new iteration-<N+1>/ directory. Repeat until the user is satisfied or you stop making meaningful progress.

4. Writing Good Test Prompts

Test prompts should be realistic, specific, and substantive. A good prompt:

  • Includes concrete details (file paths, column names, contexts).
  • Uses casual or natural language, not abstract requests.
  • Represents a task complex enough that the agent would benefit from the skill.
Weak Prompt Strong Prompt
"Format this data" "ok so my boss sent me this xlsx file (Q4 sales final FINAL v2.xlsx) and wants me to add a profit margin column. Revenue is in column C and costs are in column D."
"Extract text from PDF" "I need to pull the invoice details from /invoices/jan-2024.pdf into a CSV. There are about 50 pages with multiple invoices per page. Each invoice has an ID, date, vendor, and total."
"Create a chart" "Can you make a bar chart from the monthly active users in analytics.csv? I want to show the trend from Jan to Dec and highlight the drop in July. Save it as a PNG."
Why Detail Matters
Vague prompts don't stress-test the skill. The agent might succeed without using the skill at all, making the eval useless for measuring skill value. Detailed prompts force the agent to engage with the skill's instructions and resources.

5. Writing Good Assertions (Expectations)

Assertions are the heart of quantitative evaluation. Each assertion is a verifiable statement checked by the grader agent against the execution transcript and output files.

Principles of Good Assertions

  • Objectively verifiable — A human or script can check it without opinion.
  • Discriminating — It passes when the skill genuinely succeeds and fails when it doesn't.
  • Descriptive — The text clearly explains what is being checked.
  • Specific — "The output is a valid JSON array" is better than "The output is correct."

Examples by Skill Type

Skill Domain Good Assertion Why It Works
PDF Processing "The output CSV contains columns: invoice_id, date, vendor, total" Checks structure, not just existence
Code Generation "The generated script handles the edge case where input_file is missing" Checks behavior, not just presence of code
Data Extraction "The extracted phone numbers match the input document exactly" Checks correctness, not just presence
Document Creation "The DOCX file uses the company's letterhead template" Checks that the skill's template was used
Form Filling "All 12 fillable fields in the PDF are populated with non-empty values" Checks completeness with a specific count
Common Assertion Anti-Patterns
  • Filename-only checks: "Output file exists" passes even if the file is empty or wrong.
  • Presence without correctness: "The output includes the name 'John Smith'" passes if the name appears anywhere, even in the wrong context.
  • Too vague: "The output looks good" is not objectively verifiable.
  • Non-discriminating: Assertions that always pass in both skill and baseline configs don't measure skill value.

6. The Evaluation Pipeline

The evaluation process involves four specialized agents, each with a distinct role:

User Prompt → Executor → Grader → Comparator → Analyzer

Ex Executor Agent

Receives the test prompt (with or without the skill) and produces outputs. Saves:

  • Output files to outputs/
  • Execution transcript to transcript.md
  • Tool usage metrics to metrics.json
  • Timing data to timing.json

Gr Grader Agent

Evaluates each assertion against the executor's transcript and outputs. Produces grading.json with:

  • Pass/fail verdicts with evidence citations
  • Summary statistics (pass rate, counts)
  • Extracted and verified factual claims
  • User notes summary (uncertainties, workarounds)
  • Eval feedback (suggestions for improving assertions)

The grader also critiques the evals themselves, flagging assertions that are trivially satisfied or miss important outcomes.

Co Blind Comparator Agent

Used for advanced A/B comparisons between two skill versions. Receives outputs labeled A and B (without knowing which is which) and judges quality based on a generated rubric.

Scores outputs on content (correctness, completeness, accuracy) and structure (organization, formatting, usability), then determines a winner. This prevents bias toward a particular skill version.

An Post-Hoc Analyzer Agent

After a blind comparison, the analyzer "unblinds" the results to understand why the winner won. It compares skills, transcripts, and execution patterns to generate:

  • Winner strengths and loser weaknesses
  • Instruction-following scores
  • Actionable improvement suggestions (prioritized by impact)

8. Benchmarking & Comparison

Benchmark Aggregation

The aggregate_benchmark.py script reads all grading.json files from a workspace and produces:

  • Per-configuration statistics — mean, stddev, min, max for pass rate, time, and tokens.
  • Delta — Difference between skill and baseline configurations.
  • Per-run details — Individual expectation results and notes.
# Aggregate results from an iteration directory
python -m scripts.aggregate_benchmark \
  <workspace>/iteration-1 \
  --skill-name my-skill \
  --skill-path /path/to/my-skill

Benchmark JSON Schema

The generated benchmark.json contains:

  • metadata — skill name, model, timestamp, eval IDs
  • runs[] — per-run results with pass rates, expectations, notes
  • run_summary — statistical aggregates for each configuration
  • notes — freeform analyst observations
Analyzer Notes
After aggregation, run the analyzer agent to surface patterns aggregate stats hide: assertions that always pass (non-discriminating), high-variance evals (possibly flaky), and time/token tradeoffs. These notes go into the benchmark.json notes field.

9. Reviewing Results

The generate_review.py script creates an interactive HTML viewer for eval results. It supports two modes:

Server Mode (Claude Code)

nohup python eval-viewer/generate_review.py \
  <workspace>/iteration-1 \
  --skill-name "my-skill" \
  --benchmark <workspace>/iteration-1/benchmark.json \
  > /dev/null 2>&1 &

Opens a browser with two tabs: Outputs (click through each test case, leave feedback) and Benchmark (quantitative comparison with pass rates and timing).

Static Mode (Cowork / Headless)

python eval-viewer/generate_review.py \
  <workspace>/iteration-1 \
  --skill-name "my-skill" \
  --benchmark <workspace>/iteration-1/benchmark.json \
  --static /tmp/eval_review.html

Writes a standalone HTML file. Feedback is downloaded as feedback.json when the user clicks "Submit All Reviews."

Feedback Format

{
  "reviews": [
    {"run_id": "eval-0-with_skill", "feedback": "the chart is missing axis labels"},
    {"run_id": "eval-1-with_skill", "feedback": ""},
    {"run_id": "eval-2-with_skill", "feedback": "perfect, love this"}
  ],
  "status": "complete"
}

Empty feedback means the user thought it was fine. Focus improvements on test cases with specific complaints.

10. The Iteration Loop

Skill development is iterative. Each cycle follows this pattern:

  1. Apply improvements to the skill based on feedback and benchmark analysis.
  2. Rerun all test cases into a new iteration-<N+1>/ directory, including baselines.
  3. Launch the viewer with --previous-workspace pointing at the previous iteration for comparison.
  4. Wait for human review and read feedback.json.
  5. Repeat until the user is happy, feedback is all empty, or progress stalls.

Improvement Principles

  • Generalize from feedback. Don't overfit to the test cases. If an issue is stubborn, try different metaphors or patterns rather than adding rigid MUST rules.
  • Keep the prompt lean. Remove instructions that aren't pulling their weight. Read transcripts, not just final outputs.
  • Explain the why. Modern LLMs have good theory of mind. Explain reasoning instead of relying on heavy-handed rules.
  • Bundle repeated work. If test transcripts show agents independently writing similar helper scripts, bundle that script into the skill.

11. Trigger Description Optimization

The description field in SKILL.md frontmatter is the primary mechanism that determines whether Claude invokes a skill. After creating or improving a skill, you can optimize this description for better triggering accuracy.

The Process

  1. Generate trigger eval queries — Create ~20 realistic queries (8-10 should-trigger, 8-10 should-not-trigger). Save as JSON.
  2. Review with user — Present via assets/eval_review.html for editing and approval.
  3. Run optimization loop — Use scripts/run_loop.py to automatically test and improve the description.
  4. Apply the best description — Update SKILL.md frontmatter with the result.

Example Eval Query

[
  {
    "query": "ok so my boss just sent me this xlsx file... wants me to add a column that shows profit margin",
    "should_trigger": true
  },
  {
    "query": "can you explain how pivot tables work in excel? just curious, no file to process",
    "should_trigger": false
  }
]
Triggering Mechanism
Skills appear in Claude's available_skills list with their name + description. Claude decides whether to consult a skill based on that description. Simple, one-step queries may not trigger a skill even if the description matches, because Claude can handle them directly with basic tools. Complex, multi-step, or specialized queries reliably trigger skills when the description matches.

Optimization Loop

python -m scripts.run_loop \
  --eval-set trigger_evals.json \
  --skill-path /path/to/skill \
  --model claude-sonnet-4-6 \
  --max-iterations 5 \
  --verbose

The loop splits evals into 60% train and 40% held-out test. It evaluates the current description (3 runs per query for reliability), calls Claude to propose improvements based on failures, and re-evaluates each new description. The best description is selected by test score, not train score, to avoid overfitting.
